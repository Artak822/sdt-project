# Отчёт По Реализации Проекта

## О проекте

Проект представляет собой Telegram-бота для знакомств с микросервисной архитектурой. Пользователь проходит регистрацию через Telegram, заполняет анкету, просматривает анкеты других пользователей, ставит лайки и получает мэтчи. В проекте реализованы хранение данных, событийное взаимодействие между сервисами, кэширование ленты, рейтинговая система и хранение фотографий в S3-совместимом хранилище.

Основная реализация находится в следующих частях репозитория:

- `bot/` — Telegram-бот на `Aiogram`
- `services/user_service/` — сервис пользователей и анкет на `FastAPI`
- `services/match_service/` — сервис лайков и мэтчей
- `services/rating_service/` — сервис рейтингов
- `celery_worker/` — фоновые задачи пересчёта рейтинга
- `docker-compose.yml` — общая инфраструктура проекта

## Архитектура И Инфраструктура

Проект развёрнут как набор отдельных контейнеров. В `docker-compose.yml` описаны:

- `bot`
- `user_service`
- `match_service`
- `rating_service`
- `celery_worker`
- `postgres`
- `redis`
- `rabbitmq`
- `minio`

Таким образом, в проекте реализована полноценная микросервисная схема с отдельными сервисами, общей базой данных, очередью сообщений, кэшем и S3-совместимым файловым хранилищем.

## Telegram-Бот

Telegram-бот реализован в каталоге `bot/`.

Что сделано:

- регистрация нового пользователя через `/start` и кнопку начала регистрации
- хранение пользовательского сценария через FSM
- создание анкеты через последовательный опрос пользователя
- редактирование уже существующей анкеты
- просмотр анкет других пользователей
- постановка лайков
- обработка пропусков
- показ списка мэтчей

Основные точки реализации:

- `bot/handlers/start.py` — регистрация пользователя
- `bot/handlers/profile.py` — создание и редактирование анкеты
- `bot/handlers/search.py` — просмотр ленты, лайки и пропуски
- `bot/handlers/menu.py` — дополнительные действия пользователя
- `bot/fsm/states.py` — состояния анкеты

В результате бот покрывает базовый пользовательский сценарий знакомства внутри Telegram.

## Пользователи И Анкеты

Сервис пользователей реализован в `services/user_service/`.

Что сделано:

- создание пользователя
- получение пользователя по Telegram ID
- создание анкеты
- обновление анкеты
- удаление анкеты
- получение анкеты пользователя
- получение ленты анкет

Основные файлы:

- `services/user_service/main.py` — HTTP API
- `services/user_service/crud.py` — бизнес-логика и работа с базой
- `services/user_service/models.py` — модели таблиц `users` и `profiles`
- `services/user_service/schemas.py` — схемы запросов и ответов

В анкете реализованы поля:

- имя
- возраст
- пол
- кого ищет пользователь
- город
- описание
- фото
- диапазон предпочтительного возраста

Это покрывает базовую систему анкет, необходимую для работы бота знакомств.

## Система Лайков И Мэтчей

Логика лайков и мэтчей реализована в `services/match_service/`.

Что сделано:

- сохранение лайка
- проверка взаимности лайка
- создание мэтча при взаимной симпатии
- выдача списка мэтчей пользователя
- публикация события о создании мэтча

Основные файлы:

- `services/match_service/main.py` — API сервиса
- `services/match_service/logic.py` — логика обработки лайков
- `services/match_service/crud.py` — работа с таблицами `likes` и `matches`
- `services/match_service/models.py` — модели БД
- `services/match_service/rabbitmq.py` — публикация событий в RabbitMQ

Таким образом, в проекте реализован полный цикл: пользователь ставит лайк, сервис проверяет встречный лайк и при необходимости создаёт мэтч.

## Рейтинговая Система

Система рейтинга реализована в `services/rating_service/` и `celery_worker/`.

### Уровень 1: первичный рейтинг

Первичный рейтинг рассчитывается на основе заполненности анкеты и наличия основных полей.

Что учитывается:

- имя
- возраст
- пол
- описание
- город
- поле `looking_for`
- наличие фотографии

Основной файл:

- `services/rating_service/algorithms.py` → `calc_primary_score`

### Уровень 2: поведенческий рейтинг

Поведенческий рейтинг учитывает активность анкеты в системе.

Что учитывается:

- количество полученных лайков
- количество мэтчей

Основные файлы:

- `services/rating_service/algorithms.py` → `calc_behavioral_score`
- `celery_worker/tasks.py` — периодический пересчёт на основе данных из БД

### Уровень 3: комбинированный рейтинг

Итоговый рейтинг формируется как комбинация первичного и поведенческого рейтинга.

Основной файл:

- `services/rating_service/algorithms.py` → `calc_combined_score`

### Где рейтинг применяется

Рейтинг используется при построении ленты анкет:

- `services/user_service/crud.py` → `get_feed_profiles`

При выдаче ленты анкеты сортируются по `combined_score`, поэтому более релевантные анкеты показываются выше.

## База Данных

В проекте используется PostgreSQL. Подключение и запуск базы описаны в `docker-compose.yml`.

Схема данных реализована через SQLAlchemy-модели.

Основные сущности:

- `users`
- `profiles`
- `likes`
- `matches`
- `ratings`

Файлы моделей:

- `services/user_service/models.py`
- `services/match_service/models.py`
- `services/rating_service/models.py`

Создание таблиц выполняется при старте сервисов через:

- `services/user_service/database.py`
- `services/match_service/database.py`
- `services/rating_service/database.py`

Таким образом, в проекте настроена рабочая база данных и реализована схема, необходимая для хранения пользователей, анкет, лайков, мэтчей и рейтингов.

## Redis

Redis используется в проекте не формально, а как рабочий инструмент ускорения ленты анкет.

Что сделано:

- кэширование очереди анкет для просмотра
- хранение уже просмотренных профилей
- сокращение количества повторных обращений к базе и API при свайпах

Основной файл:

- `bot/services/redis_cache.py`

Логика использования Redis подключена в:

- `bot/handlers/search.py`
- `bot/main.py`

Дополнительно Redis используется как брокер и backend для Celery:

- `celery_worker/config.py`

## RabbitMQ

RabbitMQ используется для событийного взаимодействия между частями системы.

Что сделано:

- публикация события регистрации пользователя
- публикация события завершения анкеты
- публикация события лайка
- публикация события мэтча

Основные файлы:

- `bot/services/publisher.py`
- `services/user_service/rabbitmq.py`
- `services/rating_service/rabbitmq.py`
- `services/match_service/rabbitmq.py`

Используемые события позволяют отделить действия бота от фоновой обработки в сервисах.

## Celery

Celery реализован как отдельный фоновый процесс в `celery_worker/`.

Что сделано:

- настроено Celery-приложение
- добавлены периодические задачи
- выполняется пересчёт поведенческого рейтинга
- выполняется пересчёт итогового рейтинга

- `celery_worker/celery_app.py`

Это позволяет вынести тяжёлые расчёты из пользовательского запроса и поддерживать рейтинг в актуальном состоянии.

## S3-Совместимое Хранилище

Для фотографий профилей используется S3-совместимое хранилище MinIO.

Что сделано:

- поднят сервис `minio` в `docker-compose.yml`
- настроен бакет для фотографий
- реализована загрузка фото в S3-совместимое хранилище
- реализовано формирование публичного URL фотографии
- реализовано удаление старого объекта при замене фотографии

Основные файлы:

- `bot/services/s3_client.py`
- `bot/handlers/profile.py`
- `bot/config.py`

Текущая реализация поддерживает:

- генерацию уникальных ключей объектов
- определение типа файла
- загрузку фотографии в бакет
- возврат публичной ссылки
- очистку старой фотографии при обновлении анкеты

Таким образом, хранение фотографий вынесено из Telegram и реализовано через отдельное объектное хранилище.

## Метрики И Логирование

### Логирование

Во всех основных сервисах настроено логирование через стандартный модуль `logging`.

Логирование присутствует в:

- `bot/main.py`
- `services/user_service/main.py`
- `services/match_service/main.py`
- `services/rating_service/main.py`
- `celery_worker/tasks.py`

Также логирование используется в прикладной логике сервисов и при обработке ошибок интеграций.

### Метрики (Prometheus)

Во всех трёх FastAPI сервисах подключён `prometheus-fastapi-instrumentator`. Каждый сервис экспортирует endpoint `/metrics` в формате Prometheus.

Что собирается автоматически:

- количество HTTP-запросов по методам и endpoint-ам
- латентность запросов (гистограмма)
- количество запросов в статусе 4xx и 5xx
- количество активных соединений

В `docker-compose.yml` поднят контейнер `prometheus` (порт 9090), который с интервалом 15 секунд опрашивает все три сервиса.

Конфигурация:

- `prometheus.yml` — список целей для сбора метрик
- `services/user_service/main.py` — `Instrumentator().instrument(app).expose(app)`
- `services/match_service/main.py` — аналогично
- `services/rating_service/main.py` — аналогично

Метрики позволяют отслеживать нагрузку на каждый сервис в реальном времени и выявлять деградацию производительности.

## CI/CD

Для проекта настроен CI/CD через GitHub Actions.

Основной файл:

- `.github/workflows/tests.yml`

Что делает pipeline:

- запускается при каждом пуше в ветку `main` и при открытии pull request
- устанавливает Python 3.11
- устанавливает зависимости всех сервисов и тестов
- запускает полный набор тестов через `pytest`

Это позволяет автоматически проверять корректность кода при каждом изменении и не допускать регрессий в основную ветку.

## Нагрузочное Тестирование

Нагрузочное тестирование проводилось с помощью Apache JMeter.

Основной файл:

- `jmeter/dating_bot_load_test.jmx`

Что тестировалось:

- `GET /health` и `GET /profiles/feed/{user_id}` — user_service (порт 8000)
- `GET /health` и `GET /matches/{user_id}` — match_service (порт 8002)
- `GET /health` — rating_service (порт 8001)

Параметры теста:

- 20 потоков на каждый сервис
- 10 итераций на поток
- ramp-up 5 секунд

Тест проверяет, что сервисы корректно отвечают под параллельной нагрузкой (200 одновременных запросов). Результаты сохраняются в `jmeter/results.jtl`.
